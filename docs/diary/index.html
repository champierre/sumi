青が暗くなりすぎる — --gray-model colorimetric

同じ PDF を sumi と Ghostscript でグレースケールにすると、原色、とくに青の濃さが大きく違いました。 sumi のほうが暗く、純粋な青はほとんど黒になります。 基本色で塗った矩形の PDF を変換し、出力の g 演算子の値を比べました （0 が黒、1 が白。Ghostscript 10.02.1）。

RGB をグレーにした値
元の色luma（0.1.0）colorimetricGhostscript（既定）Ghostscript（ICC なし）
赤 (1, 0, 0)0.3000.4980.5060.298
緑 (0, 1, 0)0.5900.8620.8630.588
青 (0, 0, 1)0.1100.2980.2710.110
(0.2, 0.4, 0.8)0.3840.4180.4080.380

手がかりは右端の列です。Ghostscript も ICC を使わない変換（-dUseFastColor=true）では sumi とほぼ同じ値になります。差は計算のしかただけから来ていました。 sumi はガンマ補正済みの RGB の値にそのまま 0.30・0.59・0.11 を掛けます。 Ghostscript は既定で、sRGB をリニアな値に戻してから輝度を求め、グレーに戻します。 くっきりした原色ほど差が大きく、係数のいちばん小さい青がいちばん暗く出ます。

考え直したこと: Rec.709 の係数を使わなかった理由

README の「仕様との差分」には、Rec.709 の係数はリニア値向けなので PDF 仕様の式に合わせた、 と書いていました。合わないのは係数だけを持ってくることで、 値をリニアに戻してから使えば、見た目の明るさに合った変換になります。 colorimetric はそのとおりに、リニアに戻して Rec.709 の係数で輝度を求め、 sRGB の曲線で戻します。既定は今までどおり luma で、0.1.0 と同じ出力になります。

同じ式を、色演算子、Indexed のパレット、画像、シェーディング、注釈の色、 モノクロの閾値判定のすべてで使います。8 bit の画像は、8 bit からリニアへの表と、 輝度から 8 bit への表の 2 つを引くだけにして、画素ごとの計算を増やしていません。 無彩色（R = G = B）の値は、どちらの式でも変わりません。

結果を JSON で受け取る — --report json

これまでの -v の出力は人が読むための文章で、警告も sumi: warning: ... という文字列で出るだけでした。 呼び出す側がページ数や警告を使うには文章を解析するしかなく、文言を変えれば壊れます。 --report json を付けると、終わるときに結果を 1 行の JSON で標準エラーに出します。 失敗したときも同じ形です。 

{"status":"error","exit_code":4,"mode":"grayscale","gray_model":"luma","report":null,
 "error":{"kind":"unsupported","message":"unsupported PDF features: image not converted: YCCK (Adobe CMYK) JPEG image",
          "details":["image not converted: YCCK (Adobe CMYK) JPEG image"]}}

上は、白黒反転のバグのあとで未対応にした YCCK の JPEG を、 --strict 付きで変換したときの出力です（読みやすいように改行しています）。

  • 出力先は標準エラー — 標準出力は -o - で PDF を書くのに使うためです。このとき警告と -v の件数は文章で出さず、標準エラーには JSON の 1 行だけが出ます
  • キーは常にすべて出す — 当てはまらないものは null か空の配列にします
  • 処理を分けるのは error.kind で — message の文言は変わることがあります
  • 依存を増やさない — JSON は手で組み立てています。serde_json はテストでだけ使います
できなかったこと: 引数の誤りは JSON にならない

存在しないオプションなど、引数の書き方の誤りは文章のまま出ます。 引数を読む段階で失敗するので、--report json が指定されたかどうかを まだ判断できないためです。

gem で配る — sumi-ruby

Rails アプリケーションで sumi を使うには、これまで環境ごとに手作業が要りました。 本番の Dockerfile では GitHub Releases から curl で取ってきて アーキテクチャごとに SHA256 を確かめ、開発者はそれぞれ取ってきて PATH に置きます。 バージョンを上げるたびにその全部を直し、それでも環境ごとにずれやすい状態でした。

そこで tailwindcss-ruby と同じ形で、 プラットフォームごとにビルド済みの実行ファイルを同梱した gem を作りました。 Gemfile.lock でバージョンが固定されるので、開発環境・CI・本番で同じ sumi が動きます。

  • 名前 — sumi は RubyGems で使われていたので sumi-ruby にしました。バージョンは sumi と同じにし、リリースのときに食い違っていれば止めます
  • Linux — musl の静的リンク版を、gnu と musl の両方の gem に入れます。glibc の環境でも Alpine でも同じ実行ファイルが動きます
  • 公開 — リリースのワークフローが、CLI のアーカイブから gem を組み立て、Trusted Publishing で RubyGems.org に出します

0.2.0 では、7 つのプラットフォーム（Linux 4、macOS 2、Windows 1）の gem と、 実行ファイルを含まない ruby 版の、あわせて 8 つを公開しました。

気をつけること: 実行ファイルのない gem が入ることがある

Bundler は Gemfile.lock の PLATFORMS にあるプラットフォームの gem を選びます。 ここに ruby しかないと実行ファイルを含まない gem が入り、実行したときに初めてエラーになります。 Mac で開発して Linux で動かすような場合は、 bundle lock --add-platform で使うプラットフォームを足しておく必要があり、 gem の README に書きました。

出力を小さくする — object stream と xref stream

0.1.0 は、ページやフォントなどの辞書を 1 つずつ、圧縮しないまま書き出していました。 相互参照表も従来のテキスト形式です。写真を含まない PDF でも mutool より大きくなるのは、 中身ではなく保存のしかたの差でした。

lopdf の SaveOptions を使い、辞書を object stream にまとめて圧縮し、 相互参照表を xref stream で書くようにしました。どちらも PDF 1.5 の機能なので、 1.4 以前の入力はヘッダーのバージョンを 1.5 に上げます。 圧縮されていないストリームも Flate で圧縮します（XMP メタデータは除く）。

採らなかった案: 圧縮レベルを 9 に上げる

サイズは 1% ほどしか減らず、大きな PDF では 2〜4 倍遅くなりました。 既定の圧縮レベル（6）のままにしています。

引き換えに遅くなった

変更の前後を Intel の Mac で比べると、50 ページの請求書では実行時間が約 3 割、 メモリ使用量が約 6 割（19 MB → 31 MB）増えました。ほかの 5 件はほとんど変わりません。 README の実行時間とメモリの表は 0.1.0 で測ったままで、取り直したのはサイズだけです。 README にもそう書いています。

つまずき — mutool が無言で落ちる

Mac で mutool recolor 1.28.3 に、グラデーション（Shading）を含む PDF を渡すと セグメンテーション違反で落ちます。 メッセージは出ず、出力ファイルもできないので、 終了コードを見ないと成功と区別がつきません。 計測に使った 6 件のうち 3 件が該当しました。

つまずき: 終了コードを $(...) で潰して 0 件と数えた

最初はクラッシュを 1 件も検出できませんでした。原因は 2 つあります。 シェルでは echo "$(basename "$f"): rc=$?" のように書くと、 $? が basename の結果に上書きされます。 Python の subprocess でも、シグナルによる終了は 139 ではなく 負の値で返るため、 returncode == 139 では数えられません。 終了コードは先に変数へ控え、Python 側は returncode < 0 で判定します。

原因は MuPDF のスタックの使い方でした。再帰ではなく、 関数 1 つ分のフレームがスタック全体より大きいという形です。 source/pdf/pdf-shade-recolor.c の fz_recolor_shade_type1 が、 次の配列をスタックに置いています。 

#define FUNSEGS 256
float out[(FUNSEGS+1)*(FUNSEGS+1)*FZ_MAX_COLORS];

FZ_MAX_COLORS は 32 なので 257 × 257 × 32 × 4 = 8,454,272 バイト。これが 1 フレームのほぼ全体を占めます。

フレームの大きさと、macOS のスタック上限
項目バイト
pdf_recolor_shade の 1 フレーム8,455,008
macOS のメインスレッドのスタック（ulimit -s 8176 KB）8,372,224
超過分82,784

82,784 バイト足りません。 fz_recolor_shade_type1 は pdf_recolor_shade に インライン展開されていて、確保は関数の入口で無条件に行われます。 シェーディングの種別を見る前に落ちるということです。 実際、落ちた 3 本はどれも ShadingType 2（軸）と 3（放射）で、 この配列を使う ShadingType 1（関数ベース）は 1 本も含まれていませんでした。

ファイル依存に見えたものの正体は、Shading を含むかどうかでした。 リポジトリ内の PDF 27 本と、Wikimedia Commons から集めた実 PDF 230 本の 2 通りで確かめています。

落ちた 35 本はすべて Shading を含み、含まない 195 本は 1 本も落ちませんでした。 さらに 35 本すべてが、スタックを広げるだけで正常終了しています。 例外はどちらの方向にもありません。 Mac では次のようにすれば動きます。

環境依存であって、版依存ではありません。 Intel（x86_64、macOS 14.8.7）と Apple Silicon（arm64、macOS 26.5.2）の 2 台で同じ結果になり、CPU 種別にも OS 版にもよりませんでした。 一方、計測に使った Linux（Omarchy 4.0.1、mutool 1.28.0）では 6 件とも完走します。 pdf-shade-recolor.c は 1.28.0 と 1.28.3 で同一なので、 違うのはスタックの上限だけです。 master（2026 年 9 月 12 日時点）でも当該箇所は同じでした。

測る指標

  • 変換成功率 — CLI の終了コード（0 成功 / 3 不正な PDF / 4 未対応・暗号化 / 5 入出力 / 6 時間切れ）
  • 色残り — 出力を 150dpi で描画し、RGB の最大と最小の差が 3 を超える画素を数える
  • 表示崩れ — インクのある位置が動いていないか
  • テキスト保持 — pdftotext の抽出結果が変換前後で一致するか
つまずき: 輝度差で「崩れ」を測ると CMYK 文書が全滅する

最初は変換前後の輝度差で崩れを測りました。ところが CMYK の fixture が 崩れ 0.0206 と出ます。調べると、ずれた画素は輝度 128 → 178 と 明るくなる方向で、最大差は 50 でした。 これは仕様書にある「CMYK は簡易式を使うため ICC 管理より明るくなる」 （シアン 100% は 0.70、poppler は約 0.5 ＝ 255 換算で約 51）と一致します。

色を変えるのが仕事のツールを輝度差で測るのが誤りでした。 インクのある位置（輝度 200 未満の画素）が動いたかで測る方式に作り直し、 さらに増減を分けました。monochrome で薄い色が白に飛ぶのは仕様どおりなので 「消えた」側に、塗り潰しや黒化は「増えた」側に出ます。 崩れとして扱うのは増えた側だけです。これで monochrome の誤検出が 39.7% から 0% になりました。

つまずき: 閾値の際にある明るい色を誤検出した

grayscale で 1 件だけインクが 17% 消えました。調べると彩度 186 の黄緑 （R=167 G=215 B=29）で、仕様の係数で計算すると 167×0.30 + 215×0.59 + 29×0.11 = 180。実測の輝度 180 と完全に一致します。 明るい黄緑が明るいグレーになっただけで、私が決めた閾値 200 のすぐ際にあったのが原因でした。 閾値をまたいだうえで 25 以上動いた画素だけを数えるようにして解消しています。

見落とし: 進捗が見えない作りだった

件数を出す処理は書いていたのに、標準出力がパイプ越しにバッファされて届かず、 結果ファイルも完了時にしか書かれない設計でした。 30 分走らせても「どこまで進んだか」を答えられない状態だったので、 10 件ごとに件数・速度・残り時間を即時出力し、 validation/progress-<mode>.txt にも書くよう直しました。

大きすぎる画像が測定から漏れる

検証ログに DecompressionBombWarning が出ています。 画像処理ライブラリが 8,900 万画素を超える画像のデコードを拒否するため、 大判のポスターや地図を 150dpi で描画したページは測定がスキップされます。 1008 件で 4 回だけだったので、結果への影響は小さいと判断しました。

見つかったバグ — Adobe の CMYK JPEG が白黒反転する

表示崩れとして検出された 10 件のうち 9 件が同じ原因でした。 Adobe 系のツールが書き出した CMYK の JPEG（APP14 の transform が 2、YCCK）を 含む PDF を変換すると、ほぼ白いポスターがほぼ真っ黒になります。

ポスター 1 枚のグレー値（平均）
測りかたグレー値
元の見た目168.7
sumi の出力（修正前）28.0
元の画像を反転してから変換162.7

元との相関が -0.900、元を反転したものとの相関が +0.900 で、 反転しているのは明らかでした。原因は sumi ではなく、JPEG のデコードに使っている zune-jpeg 側にあります。YCCK を RGB にデコードすると色が反転します （0.5.15 と 0.5.16-rc2 の両方で確認）。

直せなかった直しかた

最初は「デコーダに CMYK 出力を要求すればよい」と考えましたが、 Unimplemented colorspace mapping from YCCK to CMYK で失敗しました。 次に「返ってきた RGB を反転すればよい」と考えましたが、これも 226.8 にしかならず、 正解の 168.7 には戻りません。正しい値は、生の 4 成分を反転した場合にだけ出ます。

そこで YCCK は未対応として扱い、画像を元のまま残して警告を出す ことにしました。黙ってページを黒くするより、色が残るほうが害が小さいためです。 該当 9 件で黒化は消え、元との相関は +0.96〜+1.00 に戻りました。 引き換えに、これらの文書では色が残ります（色残りの割合は平均 0.00 から 0.30 へ）。 transform が 0 や 1 の通常の CMYK JPEG は、これまでどおり変換されます。

再発を防ぐため、YCCK の JPEG を埋め込んだ 1.3KB の PDF を fixtures/ycck_jpeg.pdf として追加し、警告が出ることと画像が 変換されないことを確かめるテストを書きました。

つまずき: 検証中にバイナリを差し替えてデータを失った

monochrome の 1 回目は、実行中に cargo build を走らせてしまい、 前半と後半で別のバイナリを測っていました。同じ入力なのにインクの増加が 0.745 と 0.000 に分かれたのを不審に思って調べるまで、気づけませんでした。 結果はすべて破棄し、書き込み禁止にしたコピーを SUMI_BIN で指定して流し直しています。

「どのバイナリで測ったか」を固定できない作りだったのが原因です。 測定の最中に測定対象を変えてしまえば、どんなに件数を増やしても意味がありません。

白黒反転の原因は sumi ではなく、JPEG のデコードに使っている zune-jpeg 側にありました。 調べた内容を開発元に報告し、修正も提案しています。
