1. まず全体を眺める

これまでの 2 回より倍以上長いファイルですが、部品は 5 つに分かれます。 切れ端の型、バイトの分類、切り分ける本体、切れ端を値に戻す関数、テストです。

1〜2 行目のコメントに、このファイルの狙いが書いてあります。 

//! Content stream tokenizer that keeps byte offsets, so the rewriter can replace individual
//! operators and copy everything else verbatim.

「バイト位置を覚えておくコンテンツストリームのトークナイザ。 おかげで書き換え側は、個々の命令だけを置き換えて、ほかは一字一句そのまま写せる」。 切り分けるだけなら簡単ですが、「位置を覚える」が、このファイルの設計を決めています。 理由は 3 節で分かります。

2. 字句解析とは — 1 0 0 rg を 4 つに切る

PDF のしくみで見たとおり、ページの中身は次のような命令の並びです。 

1 0 0 rg
/F1 12 Tf
(Hello) Tj

人が見れば「赤にする」「フォント F1 を 12 ポイントで」「Hello を書く」と読めますが、 プログラムにとっては 1 0 0 rg\n/F1 12 Tf\n(Hello) Tj という 1 本のバイト列です。 これを意味のある最小の切れ端に分ける仕事を字句解析（lexical analysis）、 する部品を lexer または tokenizer、切れ端を token と呼びます。 ファイル名の lexer.rs はここから来ています。

図の右側がこのファイルの出力です。 「1」という文字ではなく「0 バイト目から 1 バイト目まで」という位置を返しています。 これが 1 行目のコメントにあった「バイト位置を覚えておく」の意味です。

3. 切れ端の形 — Kind と Token

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub(crate) enum Kind {
    Number,
    Name,
    String,
    ArrayOpen,
    ArrayClose,
    DictOpen,
    DictClose,
    /// Operators, `true`/`false`/`null` and stray bytes.
    Keyword,
}

#[derive(Debug, Clone, Copy)]
pub(crate) struct Token {
    pub kind: Kind,
    pub start: usize,
    pub end: usize,
}

切れ端の種類は 8 つです。PDF の値の種類と見比べると、対応がすぐ分かります。

切れ端の種類と、コンテンツストリームでの書き方
Kind書き方PDF での意味
Number1 0.5 -3.数値（整数と小数の区別はここではしない）
Name/F1 /DeviceRGB名前
String(Hello) <48656c>文字列（括弧のものと 16 進のもの）
ArrayOpen / ArrayClose[ ]配列の始まりと終わり
DictOpen / DictClose<< >>辞書の始まりと終わり
Keywordrg Tj true命令、true/false/null、それ以外の変なバイト

配列と辞書は「始まり」と「終わり」の記号を別々の切れ端にするだけで、 中身をまとめて 1 つの配列にはしません。 入れ子をたどるのは字句解析の次の段階（構文解析）の仕事で、 このファイルでは 10 節の parse_object が、必要なときだけそれをします。

Keyword のコメントに「stray bytes（はぐれたバイト）」とあります。 たとえば対応する ( のない ) のような、どの種類にも当てはまらないバイトも、 エラーにせず 1 バイトの Keyword にします。 lexer は決して失敗しません。 前回の「寛容に読む」が、ここでも貫かれています。

なぜ文字ではなく位置を持つのか

Token の中身は kind、start、end の 3 つだけ。 切れ端の文字そのものを持たないのは、sumi の仕事が「命令の置き換え」だからです。

sumi が書き換えたいのは 1 0 0 rg のような色の命令だけで、 文字の位置や字形、パスの座標には触りたくありません。 触らないことを確実にするいちばん簡単な方法は、元のバイト列を、書き換える範囲以外そのままコピーすることです。 そのためには「どこからどこまでが 1 0 0 rg だったか」の位置が要ります。 文字を切り出して持ってしまうと、逆に位置が分からなくなります。

Rust メモ：usize と、start..end

usize は「大きさや位置を表す整数」で、負になりません。 配列の何番目、バイト列の何バイト目、といった値にはこの型を使います。

start..end は「start 以上 end 未満」の範囲です。 0..1 なら 0 バイト目だけ、6..8 なら 6 と 7 バイト目。 終わりを含まないので、長さは end - start、 次の切れ端は end から始まる、と計算がきれいになります。

Rust メモ：PartialEq, Eq

Kind の derive には、第 1 回で見た Debug, Clone, Copy に加えて PartialEq, Eq があります。これは == で比べられるようにする指定です。 呼ぶ側の token.kind != Kind::Keyword のような比較は、これがないと書けません。 Token に付いていないのは、位置まで含めて 2 つの切れ端を比べる場面がないからです。

3 つとも小さな値なので、Token 全体で 24 バイトです（実測）。 1 ページ分の切れ端をすべて Vec に入れても、数十 KB で済みます。

4. バイトを 3 つに分ける — is_whitespace など

pub(crate) fn is_whitespace(b: u8) -> bool {
    matches!(b, b'\0' | b'\t' | b'\n' | b'\x0c' | b'\r' | b' ')
}

pub(crate) fn is_delimiter(b: u8) -> bool {
    matches!(
        b,
        b'(' | b')' | b'<' | b'>' | b'[' | b']' | b'{' | b'}' | b'/' | b'%'
    )
}

pub(crate) fn is_regular(b: u8) -> bool {
    !is_whitespace(b) && !is_delimiter(b)
}

切り分けの土台は、1 バイトを 3 種類のどれかに分類することです。 PDF 仕様（7.2.2）が、そのとおりに 3 つに分けています。

PDF 仕様 7.2.2 の 3 分類
分類バイト役目
空白（white-space）NUL、タブ、改行、改ページ、復帰、スペースの 6 つ切れ目。何個並んでも 1 つの切れ目
区切り（delimiter）( ) < > [ ] { } / % の 10 個切れ目であり、それ自身が意味を持つ
普通（regular）それ以外すべて数、命令、名前の本体

大事なのは、区切りは前後に空白がなくても切れ目になることです。 (Hello)Tj も [.5]TJ も、空白なしでつながって書けます。 逆に「普通」のバイト同士は、空白がないとつながってしまいます。 7 節の実測で、1 0 0rg と書くとどうなるかを見ます。

Rust メモ：u8、b'…'、matches!

u8 は 0〜255 の整数、つまり 1 バイトです。 b' ' は「スペースのバイト（32）」のように、文字をバイトの数値として書く書き方です。 b'\x0c' は 16 進で 0C、改ページのバイトです。

matches!(b, A | B | C) は「b が A か B か C なら true」。 第 1 回の match を、真偽を返すだけの 1 行に縮めた書き方です。 末尾の ! は、関数ではなくマクロ（コンパイル前に展開される定型文）である印で、 前回の vec! と同じ仲間です。

5. 読む位置を覚える — Lexer

pub(crate) struct Lexer<'a> {
    data: &'a [u8],
    pos: usize,
}

impl<'a> Lexer<'a> {
    pub(crate) fn new(data: &'a [u8]) -> Self {
        Lexer { data, pos: 0 }
    }

    pub(crate) fn data(&self) -> &'a [u8] {
        self.data
    }

    pub(crate) fn text(&self, token: Token) -> &'a [u8] {
        &self.data[token.start..token.end]
    }

Lexer が持つのは、読んでいるバイト列（data）と、いま何バイト目まで読んだか（pos）の 2 つだけです。 new は先頭（0）から始める。text は、切れ端の位置から実際のバイト列を切り出す。 切れ端が位置しか持たないぶん、文字が欲しいときはこの text に切れ端を渡します。

data が借り物（&）であることに注意してください。 Lexer はバイト列をコピーしません。 前回の decode_stream が展開した結果を、そのまま借りて読みます。 何 MB のページでも、Lexer 自体は 24 バイトです（実測。借り物の場所と長さで 16 バイト、pos で 8 バイト）。

Rust メモ：struct にも付く 'a

前回、関数に付く 'a（ライフタイム）を見ました。今回は struct に付いています。 Lexer<'a> は「この struct は、'a のあいだ生きている何かを借りている」という宣言です。 借りているのは data で、元のバイト列より長生きすることはできません。

text の戻り値が &'a [u8] なのが肝です。 「Lexer が生きているあいだ」ではなく「元のバイト列が生きているあいだ」使える、と言っています。 だから呼ぶ側は、切り出したバイト列を持ったまま、Lexer を先に進めたり手放したりできます。 もし &self と同じ長さにしてしまうと、切り出した文字を見ているあいだ Lexer を動かせなくなります。 小さな違いですが、呼ぶ側の書きやすさが大きく変わります。

Rust メモ：&[u8] と Vec<u8>

前回の Vec<u8> が「自分で持っているバイト列」だったのに対し、 &[u8] は「どこかにあるバイト列の一部を借りて見ている」型です。 &self.data[token.start..token.end] は、data の一部分を切り出して借りる書き方で、 コピーは起きません。範囲を指すだけです。

6. 空白とコメントを飛ばす

    fn skip_whitespace_and_comments(&mut self) {
        while let Some(&b) = self.data.get(self.pos) {
            if is_whitespace(b) {
                self.pos += 1;
            } else if b == b'%' {
                while self.pos < self.data.len() && !matches!(self.data[self.pos], b'\r' | b'\n') {
                    self.pos += 1;
                }
            } else {
                break;
            }
        }
    }

切れ端を読む前の下ごしらえです。 いまの位置のバイトが空白なら 1 つ進む。% なら行末まで進む（PDF では % から行末までがコメント）。 どちらでもなければ止まる。

self.data.get(self.pos) は、末尾を越えていれば None を返すので、 バイト列の終わりで自然にループが止まります。 「pos が長さ未満か」をいちいち確かめる代わりに、Option に答えさせています。

Rust メモ：&mut self と while let

&mut self は「自分自身を書き換える」メソッドの印です。 pos を進めるので、5 節の text（読むだけの &self）と違って mut が要ります。

while let Some(&b) = … は「Some である限りくり返し、中身を b と呼ぶ」。 前回の if let のくり返し版です。 Some(&b) の & は、get が返す借り物（&u8）から中の値を取り出す書き方で、 1 バイトのコピーは安いので借りたままにする理由がありません。

7. 心臓部 — next_token

いよいよ本体です。67 行ありますが、骨組みは単純で、 「先頭の 1 バイトを見て種類を決め、その種類の終わりまで進む」だけです。まず骨組みから。 

    pub(crate) fn next_token(&mut self) -> Option<Token> {
        self.skip_whitespace_and_comments();
        let data = self.data;
        let start = self.pos;
        let b = *data.get(start)?;
        let (kind, end) = match b {
            // … 先頭のバイトごとに (種類, 終わりの位置) を決める …
        };
        self.pos = end.min(data.len());
        Some(Token {
            kind,
            start,
            end: self.pos,
        })
    }

空白を飛ばし、いまの位置を start として覚え、先頭のバイト b を取り出す。 match で種類と終わりを決め、pos を終わりまで進めて、Token を返す。 戻り値が Option なのは、バイト列の終わりに来たら None を返して「もう切れ端はない」と伝えるためです。

Rust メモ：? — 無ければ、ここで帰る

強調した ? は、「Some なら中身を取り出して続ける。None なら関数ごと None を返して終わる」という 1 文字です。 data.get(start) は末尾を越えていれば None なので、 バイト列を読み切ったときは、この行で next_token が None を返します。

前回の decode_stream でも ? が出てきましたが、あちらは Result（失敗なら Err を返す）でした。 ? は Option にも Result にも使えて、どちらも「だめなら早めに帰る」を 1 文字で書けます。 これを match で書くと 4 行になります。

先頭のバイトで分ける

match b の腕（分岐）は 9 つあります。短いものから見ます。 

            b'<' if data.get(start + 1) == Some(&b'<') => (Kind::DictOpen, start + 2),
            b'>' if data.get(start + 1) == Some(&b'>') => (Kind::DictClose, start + 2),
            b'[' => (Kind::ArrayOpen, start + 1),
            b']' => (Kind::ArrayClose, start + 1),
            _ if is_delimiter(b) => (Kind::Keyword, start + 1),

[ と ] は 1 バイトで終わり。<< と >> は 2 バイトで終わり。 最後の行は、3 節で触れた「はぐれたバイト」で、 ここまでのどれにも当てはまらなかった区切り（対応のない ) や } など）を 1 バイトの Keyword にして先へ進みます。

Rust メモ：match の腕に付く if

b'<' if 次のバイトも '<' のように、腕には条件を足せます（ガードと呼びます）。 上から順に試すので、< で始まっても次が < でなければこの腕は選ばれず、 次に出てくる「16 進の文字列」の腕に落ちます。 _ if is_delimiter(b) は「何でもいいが、区切りであること」という腕です。

名前と、数・命令の腕は、「普通のバイトが続く限り進む」という同じ形をしています。 

            b'/' => {
                let mut i = start + 1;
                while i < data.len() && is_regular(data[i]) {
                    i += 1;
                }
                (Kind::Name, i)
            }
            _ => {
                let mut i = start;
                while i < data.len() && is_regular(data[i]) {
                    i += 1;
                }
                let kind = if parse_number(&data[start..i]).is_some() {
                    Kind::Number
                } else {
                    Kind::Keyword
                };
                (kind, i)
            }

/ で始まれば名前。それ以外（最後の _）は、普通のバイトが続くところまで読んでから、 数として読めれば Number、読めなければ Keyword と決めます。 数かどうかの判定は 8 節の parse_number に任せています。 「rg は命令、1 は数」という区別は、この 1 行で付いています。

文字列 — 括弧の入れ子を数える

いちばん長い腕が、( で始まる文字列です。

            b'(' => {
                let mut depth = 0usize;
                let mut i = start;
                loop {
                    match data.get(i) {
                        None => break (Kind::String, data.len()),
                        Some(b'\\') => i += 2,
                        Some(b'(') => {
                            depth += 1;
                            i += 1;
                        }
                        Some(b')') => {
                            depth -= 1;
                            i += 1;
                            if depth == 0 {
                                break (Kind::String, i);
                            }
                        }
                        Some(_) => i += 1,
                    }
                }
            }

PDF の文字列は (a(b)c) のように、対になっていれば中に括弧を書けます。 だから「次の ) で終わり」ではだめで、( で深さを 1 増やし、) で 1 減らし、 深さが 0 に戻ったところが終わりです。 \ の次のバイトは \) のように意味を打ち消されているので、2 つまとめて飛ばします。

閉じ括弧のないまま終わりに来たら（None の腕）、末尾までを文字列にして終わります。 エラーにはしません。

Rust メモ：loop と、値を持って抜ける break

loop は「break するまで永遠にくり返す」ループです。 面白いのは break (Kind::String, i) のように、break に値を添えると、それが loop 全体の値になることです。 let (kind, end) = match b { b'(' => { … loop { … } } … } と読むと、 loop の値が腕の値になり、match の値になり、(kind, end) に入ります。 「終わりの位置を入れる変数を外に用意して、break の前に代入する」を、書かずに済ませています。

8. 数を読む — parse_number

pub(crate) fn parse_number(text: &[u8]) -> Option<f64> {
    let mut digits = 0;
    let mut dots = 0;
    for (i, &c) in text.iter().enumerate() {
        match c {
            b'0'..=b'9' => digits += 1,
            b'.' => dots += 1,
            b'+' | b'-' if i == 0 => {}
            _ => return None,
        }
    }
    if digits == 0 || dots > 1 {
        return None;
    }
    let s = std::str::from_utf8(text).ok()?;
    let s = s.strip_prefix('+').unwrap_or(s);
    let s = s.strip_suffix('.').unwrap_or(s);
    let (sign, body) = match s.strip_prefix('-') {
        Some(body) => (-1.0, body),
        None => (1.0, s),
    };
    let body = if body.starts_with('.') {
        format!("0{body}")
    } else {
        body.to_string()
    };
    body.parse::<f64>().ok().map(|v| sign * v)
}

第 1 回で「色の数値は lopdf を通さず、sumi が自分で f64 として読む」と書いた、その関数です。 前半で「数字と、高々 1 つの点と、先頭だけの符号」しかないことを確かめ、 後半で Rust 標準の parse に渡せる形に整えます。

Rust の "1.5".parse::<f64>() は優秀ですが、PDF の数の書き方とは少しずれています。 整える 3 行は、そのずれを埋めるためのものです。

最後の行に注目してください。 Rust の parse は 1e3（10 の 3 乗）を 1000 として読めますが、 PDF の数に指数の書き方はありません。 前半の検査がなければ、1e3 は数になってしまいます。 「Rust が読めるもの」ではなく「PDF が数と定めているもの」だけを数にする。 それが、parse に丸投げせず前半の検査を置いている理由です。 第 1 回の format_number が指数なしで書き出していたのと、表裏の関係です。

もう 1 つ。parse_number は f64 を返します。 前回、lopdf の小数は f32 で 8 桁目からずれると書きました。 色の値はここで f64 として読むので、0.30000001 は 0.30000001 のまま届きます（実測）。 第 1 回の 0.5 0.5 0.5 rg の境界が崩れない、と言えたのはこのためです。

Rust メモ：for (i, &c) in text.iter().enumerate()

.iter() でバイトを 1 つずつ、.enumerate() で「何番目か」も一緒に取り出します。 (i, &c) で番号を i、バイトを c と呼ぶ。 番号が要るのは、+ と - を先頭だけで許すためで、腕のガード if i == 0 がそれです。 b'0'..=b'9' は「0 以上 9 以下」の範囲で、..= は終わりを含みます。

Rust メモ：strip_prefix と unwrap_or

s.strip_prefix('+') は「先頭が + なら、それを除いた残りを Some で返す。違えば None」。 .unwrap_or(s) は「Some なら中身、None なら s のまま」。 2 つ合わせて「あれば取る、なければそのまま」が 1 行になります。 - のほうは match で受けているのは、取ったかどうかで符号（-1.0 か 1.0）も決めたいからです。

9. 画像の終わりを探す — inline_image_data

next_token が扱えない例外が 1 つあります。インライン画像です。 小さな画像は、別のオブジェクトにせず、コンテンツストリームの中に直接埋め込めます （PDF 仕様 8.9.7）。 

BI /W 2 /H 1 /BPC 8 /CS /G ID ←ここから画像のバイト→ EI

BI から ID までは普通の切れ端（幅、高さ、色空間などの辞書）ですが、 ID の直後から EI までは生のバイナリです。 切れ端の規則は通用しません。空白や区切りのバイトが、画素の値として平気で現れます。 困ったことに、画素の中に E I という 2 バイトが並ぶこともあります。 「次の EI まで」では、そこで切ってしまいます。 

    pub(crate) fn inline_image_data(
        &mut self,
        expected_len: Option<usize>,
    ) -> (usize, usize, usize) {
        let data = self.data;
        let data_start = (self.pos + 1).min(data.len());

        if let Some(len) = expected_len {
            let data_end = data_start.saturating_add(len);
            if data_end <= data.len() {
                let mut i = data_end;
                while i < data.len() && is_whitespace(data[i]) {
                    i += 1;
                }
                if data[i..].starts_with(b"EI") && data.get(i + 2).is_none_or(|&c| !is_regular(c)) {
                    self.pos = i + 2;
                    return (data_start, data_end, i + 2);
                }
            }
        }

        let mut i = data_start;
        while i + 1 < data.len() {
            if data[i] == b'E'
                && data[i + 1] == b'I'
                && (i == data_start || is_whitespace(data[i - 1]))
                && data.get(i + 2).is_none_or(|&c| !is_regular(c))
                && looks_like_content(&data[i + 2..])
            {
                let data_end = if i > data_start { i - 1 } else { i };
                self.pos = i + 2;
                return (data_start, data_end, i + 2);
            }
            i += 1;
        }
        self.pos = data.len();
        (data_start, data.len(), data.len())
    }

2 段構えです。

1 段目：長さが分かっているなら、それを信じる
圧縮されていない画像なら、幅 × 高さ × 色の数からデータの長さが計算できます（呼ぶ側の image.rs が計算して expected_len に渡します）。 その長さぶん飛ばした先に EI があれば、それが終わりです。中身は一切見ません。
2 段目：分からなければ、それらしい EI を探す
圧縮された画像は長さが分からないので、先頭から 1 バイトずつ EI を探します。 ただし条件を 3 つ付けます。前が空白であること、後ろが普通のバイトでないこと、 そしてその先 64 バイトが「命令の続きに見える」こと（強調した looks_like_content）。 
fn looks_like_content(rest: &[u8]) -> bool {
    rest.iter()
        .take(64)
        .all(|&c| c.is_ascii_graphic() || is_whitespace(c))
}

「命令の続きに見える」とは、表示できる ASCII 文字と空白だけでできているということです。 画像の中の偽の EI の後ろには、たいてい画素のバイナリが続くので、この検査で弾けます。 3 通り試しました。

inline_image_data の結果（実測。\x01 のような表記は 1 バイトの値）
ID より後ろ長さ画像とされた範囲残り

\x01\x02 EI Q不明\x01\x02 Q

3 行目は、偽の EI の後ろが \xff（表示できない）なので弾かれ、本物にたどり着いています。 4 行目はもっと意地悪で、偽の EI の後ろに命令のような q を置きましたが、 さらにその後ろの \x02 が 64 バイトの検査に引っかかり、やはり本物に着きました。 5 行目は、辞書が言う長さが実際より短い場合です。 長さぶん飛んだ先に EI がないので 1 段目は不成立となり、2 段目に落ちて正しい終わりを見つけています。 長さは信じるが、信じた先に EI がなければ疑う。 ここも寛容さの線引きです。

それでも見つからなければ、末尾までを画像として返します。 戻り値が 3 つ組 (データの始まり, データの終わり, EI の終わり) なのは、 書き換え側が「BI から EI の終わりまで」を丸ごと置き換えるのに、両方の位置が要るからです。

Rust メモ：saturating_add と is_none_or

a.saturating_add(b) は、足した結果が usize の上限を超えたら上限で止める足し算です。 expected_len は PDF の辞書から来た値なので、とんでもなく大きいかもしれません。 普通の + だと、桁あふれでプログラムが止まる（デバッグ時）か、小さな値に化ける（リリース時）ので、それを防いでいます。

data.get(i + 2).is_none_or(|&c| !is_regular(c)) は 「i + 2 バイト目が無いか、あっても普通のバイトでない」。 EI が末尾にあっても、EIQ のようにくっついていても正しく扱うための 1 行です。

10. 小さな読み書き — parse_object と write_object

3 節で「配列や辞書の中身はまとめない」と書きました。 唯一まとめる必要があるのが、インライン画像の辞書（BI から ID まで）です。 幅や色空間を読むには、切れ端の列を前回の Object に組み立てなければなりません。 それが parse_object です。 

pub(crate) fn parse_object(
    lexer: &Lexer,
    tokens: &[Token],
    index: &mut usize,
    depth: usize,
) -> Option<Object> {
    let token = *tokens.get(*index)?;
    *index += 1;
    let text = lexer.text(token);
    Some(match token.kind {
        Kind::Number => {
            let v = parse_number(text)?;
            if text.contains(&b'.') {
                Object::Real(v as f32)
            } else {
                Object::Integer(v as i64)
            }
        }
        Kind::Name => Object::Name(decode_name(&text[1..])),
        Kind::String => Object::String(decode_string(text), StringFormat::Literal),
        Kind::Keyword => match text {
            b"true" => Object::Boolean(true),
            b"false" => Object::Boolean(false),
            b"null" => Object::Null,
            _ => return None,
        },
        Kind::ArrayOpen if depth < 16 => {
            let mut items = Vec::new();
            loop {
                match tokens.get(*index) {
                    None => return None,
                    Some(t) if t.kind == Kind::ArrayClose => {
                        *index += 1;
                        break;
                    }
                    Some(_) => items.push(parse_object(lexer, tokens, index, depth + 1)?),
                }
            }
            Object::Array(items)
        }
        Kind::DictOpen if depth < 16 => {
            // … 配列と同じ形で、名前と値の組を集める …
        }
        _ => return None,
    })
}

切れ端を 1 つ取り、種類ごとに Object にします。 数なら、. を含むかどうかで Real と Integer に分けます。 配列なら、] が来るまで自分自身を呼んで要素を集めます。 要素がまた配列なら、その中でまた自分を呼びます。

Rust メモ：再帰と、depth の上限

関数が自分自身を呼ぶことを再帰と言います。 「配列の中に配列の中に配列」のように、入れ子がいくつ深くても同じ関数で読めるのが利点です。

欠点は、入れ子が深すぎると呼び出しの記録（スタック）があふれてプログラムが落ちることです。 [[[[[… と 10 万個書いた PDF を渡されたら、そうなります。 強調した if depth < 16 がその守りで、16 段より深い入れ子は読まずに None を返します。 インライン画像の辞書で 16 段の入れ子が要ることはないので、実用上は困りません。 スタックがあふれて落ちる実例は、開発日誌の mutool のクラッシュで見ました（あちらは再帰ではなく大きな配列が原因ですが、落ち方は同じです）。

Rust メモ：index: &mut usize — 呼ぶ側の変数を進める

index は「次に読む切れ端は何番目か」で、呼ぶ側の変数を借りて書き換えます。 *index += 1 の * は、借り物の指す先を書き換える印です。 再帰で自分を呼ぶときも同じ index を渡すので、内側で読み進めた分が外側にもそのまま伝わります。 戻り値で「何個読んだか」を返して足し合わせる代わりに、1 つの数を全員で共有しています。

逆向きの write_object

灰色にした画像を書き戻すときは、辞書を文字に戻す必要があります。それが write_object で、 parse_object をちょうど裏返した形です。名前と文字列の部分だけ見ます。

11. 名前と文字列を戻す — decode_name と decode_string

切れ端の文字は、まだ「書かれたまま」です。 名前の /Ca#66#e9 は本当は Café のバイト列だし、 文字列の (a\)b) は本当は a)b です。書き方の規則をほどいて元のバイト列に戻すのが、この 2 つです。 

pub(crate) fn decode_name(raw: &[u8]) -> Vec<u8> {
    let mut out = Vec::with_capacity(raw.len());
    let mut i = 0;
    while i < raw.len() {
        if raw[i] == b'#'
            && i + 2 < raw.len()
            && let Some(v) = std::str::from_utf8(&raw[i + 1..i + 3])
                .ok()
                .and_then(|h| u8::from_str_radix(h, 16).ok())
        {
            out.push(v);
            i += 3;
        } else {
            out.push(raw[i]);
            i += 1;
        }
    }
    out
}

# の後ろに 16 進 2 桁があれば、その 1 バイトに置き換える。なければ # をそのまま残す。 A#20B は A B に、桁が足りない A#2 は A#2 のままです（実測）。 ここでもエラーにはしません。

Rust メモ：if … && let Some(v) = …

if の条件の途中に let Some(v) = … を挟むと、 「ここまでの条件が真で、しかもこれが Some なら、中身を v として使う」と書けます。 前回の if let と && を混ぜた形で、Rust 1.88 で使えるようになった新しい書き方です。 これがない頃は、if を 2 段に分けるか、match で書く必要がありました。

decode_string は 62 行あり、このファイルで 2 番目に長い関数です。 16 進の <…> なら 2 桁ずつバイトにし（奇数桁なら最後を 0 で埋める）、 (…) なら \ の次を見て置き換えます。 \n は改行、\101（8 進）は A、\ のすぐ後ろの改行は「行の続き」として消えます。

この回のまとめ

lexer.rs は、バイト列を切れ端に分けるファイルでした。 切れ端が持つのは種類と位置だけで、文字は元のバイト列から借りて見る。 この設計のおかげで、書き換え側は命令だけを置き換え、ほかを一字一句そのまま写せます。

そして、この lexer は決して失敗しません。 閉じない括弧は末尾まで、知らないバイトは 1 バイトの命令、深すぎる入れ子は「無い」。 第 2 回の「寛容に読む」を、切れ端の段階で実現しています。 一方で、1e3 を数と認めない、長さの申告を鵜呑みにしない、と厳格な場所もありました。 PDF が定めた形だけを認め、それ以外は壊さず素通しする。その線引きが、495 行の中身です。
