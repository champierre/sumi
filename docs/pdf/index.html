PDF のしくみ

sumi のコードを読む前に、PDF というファイルが何でできているかを知っておくための読みものです。 予備知識は要りません。

この文書の方針は 1 つだけです。出てくるものは、すべて自分の手で開いて確かめられます。 441 バイトの PDF を自分で作るところから始めて、 最後は sumi が実際に何を書き換えているかまで見ます。

1. PDF は「紙の写真」ではない

PDF を「紙をスキャンした画像のようなもの」と思っている人は多いのですが、実際は違います。 PDF の中身は、ほとんどの場合「どこに何をどう描くか」という命令の並びです。

たとえば「赤い長方形を描く」なら、赤いピクセルの集まりが入っているのではなく、 次のような文字列が入っています。 

1 0 0 rg          ← これから塗る色は赤（R=1, G=0, B=0）
20 20 160 60 re   ← (20,20) から幅160 高さ60 の長方形
f                 ← 塗りつぶす

これが PDF の本質です。命令が書いてあるだけなので、 文字は文字のまま入っていて、検索もコピーもできます。 拡大しても線がなめらかなのも、画像ではなく命令だからです。

ここだけ覚えれば十分

PDF＝描画命令が書かれたテキストファイル（一部が圧縮されている）。 だから「色を指定している部分」だけを見つけて書き換えれば、 レイアウトも文字もそのままに白黒化できます。これが sumi のやっていることの全体像です。

2. 441 バイトの PDF を作る

いきなり実物の PDF を開くと、圧縮されたデータが大量に出てきて何も読めません。 そこでまず、圧縮なしの、人間が全部読める PDF を自分で作ります。 下の内容をそのまま minimal.pdf という名前で保存してください。 

%PDF-1.7
1 0 obj
<< /Type /Catalog /Pages 2 0 R >>
endobj
2 0 obj
<< /Type /Pages /Kids [3 0 R] /Count 1 >>
endobj
3 0 obj
<< /Type /Page /Parent 2 0 R /MediaBox [0 0 200 100] /Contents 4 0 R >>
endobj
4 0 obj
<< /Length 27 >>
stream
1 0 0 rg
20 20 160 60 re
f
endstream
endobj
xref
0 5
0000000000 65535 f
0000000009 00000 n
0000000058 00000 n
0000000115 00000 n
0000000202 00000 n
trailer
<< /Size 5 /Root 1 0 R >>
startxref
278
%%EOF

これで本当に開ける PDF です。ダブルクリックすると、 横 200・縦 100 の小さなページに、赤い長方形が 1 つ描かれているのが見えます。

なぜ手で作るのか

PDF は「難しくて中身が見えないもの」に思えますが、 いちばん小さい形はこの 25 行がすべてです。 実物の PDF が読めないのは、仕組みが複雑だからではなく、圧縮されているからです。 仕組み自体はこの 25 行から増えません。

この 441 バイトの中に、PDF のほぼすべての概念が入っています。 次の節から、これを 4 つの部品に分けて読んでいきます。

3. PDF を作る 4 つの部品

さきほどのファイルは、役割の違う 4 つの部分でできています。

おもしろいのは読む順番です。PDF は前から順に読むのではなく、 末尾から読み始めます。

4. 部品 1 — オブジェクト

PDF の中身は、すべてオブジェクトという単位で書かれています。形はいつも同じです。 

3 0 obj
<< /Type /Page /MediaBox [0 0 200 100] >>
endobj

先頭の 3 がオブジェクト番号です（次の 0 は世代番号。ほぼ常に 0 で、気にしなくて構いません）。 ほかの場所から 3 0 R と書けば、このオブジェクトを指せます。 R は reference（参照）の意味です。

オブジェクトの中に書ける値は、次の 8 種類しかありません。

PDF に出てくる値の種類
種類書き方説明
数値42 0.5 -3整数と小数。指数表記は使えません
名前/Type /Page/ で始まる識別子。キーや定数に使う
文字列(Hello)丸括弧で囲む。<48656C> と 16 進でも書ける
配列[0 0 200 100]角括弧。型が混ざってもよい
辞書<< /A 1 /B 2 >>キーと値の組。PDF の主役
真偽true false
ヌルnull
参照3 0 R別のオブジェクトを指す

辞書（<< … >>）が最重要です。 PDF のほぼすべては「辞書の中に辞書や参照が入れ子になったもの」でできています。 JSON を知っていれば、<< >> が { }、/Type がキー名だと思えばほぼ合っています。

ストリーム — 辞書にデータをぶら下げる

画像やページの描画命令のような「大きなデータ」は、辞書のあとに stream として置きます。 

4 0 obj
<< /Length 27 >>        ← データが何バイトあるか
stream
1 0 0 rg
20 20 160 60 re
f
endstream
endobj

実物の PDF では、ここにさらに /Filter /FlateDecode が付きます。 これは「この中身は zip 圧縮してあります」という意味です。 実物の PDF をテキストエディタで開くと文字化けして見えるのは、ほぼこれが理由です。 展開すれば、さきほどと同じ読める命令が出てきます。

5. 部品 2 — ページツリー

オブジェクトはファイル内にバラバラに置かれています。 「1 ページ目はどれか」は、参照をたどって知ります。入口は trailer の /Root です。

/MediaBox [0 0 595 842]
ページの大きさ。単位はポイント（1/72 インチ）です。 595×842 はちょうど A4 にあたります。 原点 (0,0) は左下で、画面座標とは上下が逆です。
/Contents 4 0 R
このページに何を描くかを書いたストリームへの参照。次節の主役です。
/Resources
そのページが使うフォントや画像の一覧。 描画命令の中では /F1 のような短い名前で呼ばれ、実体はここから引きます。

6. 部品 3 — コンテンツストリーム

ページの見た目を決めているのがコンテンツストリームです。 ここだけは書き方が独特で、値を先に、命令を後に書きます。 

20 20 160 60 re
└──── 引数 ────┘ └命令

電卓の「2 3 +」と同じ並び（逆ポーランド記法）です。 慣れると読むだけなら簡単で、行末の 1〜3 文字が命令、その手前が引数だと思えば読めます。

実物を見る

これは fixtures/libreoffice_table.pdf の中身を展開したものです（表のある実際の PDF です）。 

0.1 w                              線の太さを 0.1 に
q                                  いまの状態を保存
0 0.028 595.275 841.861 re         ページ全体の長方形
W* n                               そこだけ描画を許す（クリップ）
0.10196 0.3098 0.74901 rg          これから塗る色は青
56.7 685.939 141.75 19.45 re f*    長方形を塗る（表の見出し）
198.5 685.939 77.85 19.45 re f*    同じ色のまま次のセル
1 1 1 rg                           色を白に変更
56.7 666.439 141.75 19.45 re f*    白いセル
BT                                 ここからテキスト
56.8 753.289 Td /F1 22 Tf          位置と、フォント F1 の 22pt
[<0102>-3<03>1<04>]TJ              文字を描く
ET                                 テキスト終わり

重要なのは 色の指定が一度出ると、次に変わるまでずっと続くことです。 上の例でも 0.10196 0.3098 0.74901 rg のあとの長方形は、 すべて同じ青で塗られています。この「状態が続く」性質は、あとで効いてきます。

よく出てくる命令
命令意味例
re長方形20 20 160 60 re
m / l移動 / 直線10 10 m 90 90 l
cベジェ曲線—
f / f*塗るf
S線を描くS
q / Q状態の保存 / 復帰q … Q
BT / ETテキストの開始 / 終了BT … ET
Tj / TJ文字を描く(Hi) Tj
Do画像などを貼る/Im1 Do
q と Q は入れ子になる

q で現在の状態（色・線幅・座標系）を積み、Q で戻します。 つまり 色の状態はスタックで管理されています。 これを正しく追わないと、Q で戻ったあとの色を間違えます。 sumi も同じようにスタックを持って状態を追いかけています。

7. 部品 4 — xref と trailer

xref は「何番のオブジェクトが、ファイルの何バイト目にあるか」の索引です。 1000 ページの PDF でも、目的のオブジェクトへ一発で飛べます。 

xref
0 5                        0 番から 5 個ぶん
0000000000 65535 f         0 番は未使用（f ＝ free）
0000000009 00000 n         1 番は 9 バイト目（n ＝ 使用中）
0000000058 00000 n         2 番は 58 バイト目
0000000115 00000 n
0000000202 00000 n
trailer
<< /Size 5 /Root 1 0 R >>  全 5 個、入口は 1 番
startxref
278                        xref 自体は 278 バイト目にある
%%EOF

オフセットは実測のバイト位置なので、 オブジェクトを 1 バイトでも増減させると、以降の数字がすべてずれます。 PDF を書き換えるツールが必ず xref を作り直すのはこのためです。

PDF が「壊れている」とはどういうことか

よくあるのは xref の数字が実際の位置と合っていない状態です。 多くのビューアは黙って全体を走査し直して開いてしまうので、気づかれません。 sumi も同じように、壊れた xref を修復して読み込みます。

更新は「追記」でおこなう

PDF は末尾から読むので、ファイルの後ろに「変更したオブジェクトと、新しい xref」を 継ぎ足すだけで更新できます（incremental update）。 注釈を付けて保存した PDF が元より大きくなるのはこのためです。 古い内容は消えずに残ります。

新しい形式 — xref ストリームとオブジェクトストリーム

PDF 1.5 以降では、xref 自体を圧縮したストリームとして持つ形式と、 小さなオブジェクトをまとめて 1 つの圧縮ストリームに詰める形式が使えます。 考え方は同じですが、テキストエディタで開いても読めなくなります。 実物の PDF を開いて xref という文字が見当たらないときは、この形式です。

8. 色はどう指定されているか

ここが sumi の本題です。PDF の色指定にはいくつも書き方があり、 これを網羅することが白黒化の本質的な難しさです。

いちばん基本の 3 つ

デバイス色の指定（小文字＝塗り、大文字＝線）
命令色空間引数例
g / Gグレー10.5 g（中間の灰色）
rg / RGRGB31 0 0 rg（赤）
k / KCMYK40 1 1 0 k（赤）

値は 0〜1 です。255 ではありません。 小文字が塗りつぶしの色、大文字が線の色で、常に対になっています。

やっかいなほう — 名前付きの色空間

実際の PDF では、色空間を先に宣言してから数値を渡す書き方もよく出てきます。 

/CS0 cs          Resources の /CS0 という色空間を使う
0.2 0.4 0.9 scn  その色空間での値

この scn が難物です。引数の個数も意味も、/CS0 が何かによって変わります。 /CS0 の正体を /Resources から引いて調べないと、数値の意味が確定しません。

名前付き色空間の主な種類
種類中身例
ICCBased実質は 1/3/4 成分（グレー/RGB/CMYK）いちばん多い
Indexed色見本表の「何番」を指す3 scn ＝ 3 番の色
Separation特色 1 つの濃さ。変換用の関数を持つ印刷の特色
DeviceN特色が複数同上
Pattern色ではなく模様やグラデーション/P0 scn
なぜ sumi のコードが 5,500 行あるのか

「色を灰色にするだけ」なら数十行で済みそうに見えます。 行数の大半は、この色空間の種類ぶんの処理と、 画像・グラデーション・関数（Separation が持つ変換式）の解釈に使われています。 function.rs が 731 行もあるのは、PDF が色の変換式そのものを ファイル内に埋め込めるからです。

色を灰色にする計算

sumi が使っているのは、PDF 仕様が定める式そのものです。

Gray = 0.30 × R + 0.59 × G + 0.11 × B

緑の係数が大きいのは、人間の目が緑をいちばん明るく感じるからです。 同じ明るさに見える赤・緑・青を白黒にすると、緑がいちばん白く写ります。

9. sumi は何をしているか

ここまでを踏まえると、sumi の仕事は一文で言えます。

PDF を読み、各ページのコンテンツストリームを展開し、 色を指定している命令だけを灰色の命令に書き換えて、また圧縮して書き戻す。 描画の命令・文字・座標には一切触らない。

さきほどの 441 バイトの PDF を実際に変換すると、こうなります。

変換前                   変換後
1 0 0 rg          →      0.3 g
20 20 160 60 re   →      20 20 160 60 re   そのまま
f                 →      f                 そのまま

0.30 × 1 + 0.59 × 0 + 0.11 × 0 = 0.3 なので 0.3 g です。 命令が rg（3 引数）から g（1 引数）に変わっている点にも注目してください。 色空間そのものをグレーに置き換えています。

実物の表の PDF でも、まったく同じことが起きています。

変換前                              変換後
0.10196 0.3098 0.74901 rg      →     0.2958 g
56.7 685.939 141.75 19.45 re f*      56.7 685.939 141.75 19.45 re f*
1 1 1 rg                       →     1 g
0.85882 0.91372 1 rg           →     0.9067 g

座標も、長方形も、文字も、1 バイトも変わっていません。 だから変換後も文字を検索・コピーできます。

実際に手を動かす

コードを読む前に、これを試しておくと理解が早くなります。

# 変換して、何を書き換えたか報告させる
sumi fixtures/libreoffice_table.pdf -o out.pdf --overwrite --verbose
# → sumi: 1 pages, 1 content streams, 40 color operators,
#        0 images, 0 shadings converted to grayscale

「40 個の色命令を書き換えた」と報告されます。 この 40 という数が、さきほど見た rg の個数です。

10. つまずきやすいところ

座標の原点は左下
画面やブラウザと上下が逆です。y が大きいほど上になります。 re の座標を見るときに混乱しがちです。
色の値は 0〜1
255, 0, 0 ではなく 1 0 0 です。 0.10196 のような半端な数は、元が 8 ビットの 26/255 だったためです。
大文字と小文字は別の命令
rg（塗り）と RG（線）、g と G は別物です。 両方を書き換えないと、線の色だけ残ります。
色は「状態」であって「属性」ではない
図形ごとに色を持つのではなく、一度指定した色が次の指定まで続きます。 q / Q で入れ子にもなります。
実物はほぼ必ず圧縮されている
テキストエディタで開いて読めなくても、壊れてはいません。 /Filter /FlateDecode を探してください。
同じ見た目でも中身はソフトごとに違う
Chrome・Word・Illustrator が出す PDF は、構造も色の書き方もかなり違います。 fixtures/ に生成元の違う PDF が置いてあるのはこのためです。

自分で中身を覗く道具

実物の PDF は圧縮されていて読めませんが、展開は Python の標準ライブラリだけでできます。 次を unpack.py として保存してください。追加のインストールは要りません。 

import re, sys, zlib

data = open(sys.argv[1], "rb").read()
out, pos = bytearray(), 0
for m in re.finditer(rb"stream\r?\n", data):
    s = m.end()
    e = data.find(b"endstream", s)
    try:
        body = zlib.decompress(data[s:e])   # FlateDecode を解く
    except Exception:
        continue                            # 画像など、解けないものは飛ばす
    out += data[pos:s] + body
    pos = e
out += data[pos:]
open(sys.argv[2], "wb").write(out)
python3 unpack.py fixtures/libreoffice_table.pdf readable.pdf
grep -a -n " rg" readable.pdf | head -3

9:0.10196 0.3098 0.74901 rg
15:1 1 1 rg
21:0.85882 0.91372 1 rg

この文書で見てきた rg が、実物の PDF からそのまま出てきました。 できた readable.pdf をテキストエディタで開けば、 obj も stream も並んでいます。 好きな PDF で試してみてください。ここまで来れば、コードを読む準備は整っています。

この展開結果は PDF としては開けません

中身を圧縮なしにすると各オブジェクトの位置がずれるので、 7 章の xref の数字と合わなくなります。 読むための道具と割り切ってください。 きちんと開ける形で展開したいときは qpdf --qdf を使います。
